# Security Design — Project 1

## 1. Overview

Project 1 uses Amazon Cognito, API Gateway, AWS Lambda and Amazon S3 to provide authenticated cloud saving for a Godot game.

The security design follows a few important principles:

- Cognito manages user registration, authentication and password-related operations.
- API Gateway validates access tokens before allowing requests to reach Lambda.
- Lambda obtains the player's identity from the verified token claims rather than trusting an ID supplied by the game client.
- S3 objects remain private and are accessed through temporary presigned URLs.
- Lambda has limited permissions to access only the required objects in the project's S3 bucket.
- Passwords and complete save files are not sent to Lambda.

## 2. Authentication with Amazon Cognito

Amazon Cognito User Pools handle user accounts and authentication.

Players can register using a username, email address and password. Cognito manages the registration process, email verification, sign-in and password reset.

The Godot application communicates directly with Cognito over HTTPS using its JSON API. It uses the following operations:

- `SignUp` — creates a new user account.
- `ConfirmSignUp` — confirms the account using the verification code sent by email.
- `ResendConfirmationCode` — requests another verification code.
- `InitiateAuth` — authenticates the player using the `USER_PASSWORD_AUTH` flow.
- `ForgotPassword` — starts the password-reset process.
- `ConfirmForgotPassword` — completes the password reset using the verification code and new password.

Cognito is responsible for securely handling user passwords. The Godot application does not store player passwords in S3, send them to Lambda or include them in save files.

After successful authentication, Cognito returns tokens to the Godot application. The application keeps these tokens in memory while the session is active.

## 3. Access Token Validation

When the player requests an upload or download URL, the Godot application sends an HTTP POST request to API Gateway.

The request includes the Cognito access token in the `Authorization` header:

```http
Authorization: Bearer ACCESS_TOKEN
```

API Gateway uses the `GodotProjectCognitoAuthorizer` JWT authoriser to validate the token.

The authoriser checks the token against the configured issuer and audience. It also validates the token's signature and relevant time-based claims using the issuer's public signing keys.

The configured values are:

- **JWT issuer:** `https://cognito-idp.eu-north-1.amazonaws.com/eu-north-1_GzGUofS7H`
- **JWT audience:** `3ke1alihifaae1trmt2ek0pncp`
- **Identity source:** `$request.header.Authorization`

If the token is invalid or fails validation, API Gateway rejects the request before it reaches Lambda.

This means the Lambda function receives requests that have passed API Gateway's JWT authorisation.

## 4. Player Identity and Data Isolation

A player must only be able to access their own save data.

The Lambda function obtains the player's unique Cognito ID from the verified JWT claims:

```python
claims = event.get(
    "requestContext", {}
).get(
    "authorizer", {}
).get(
    "jwt", {}
).get("claims", {})

player_id = claims.get("sub")
```

It also checks that the token is an access token:

```python
if claims.get("token_use") != "access":
    return response(401, {
        "error": "Access token required"
    })
```

The function validates the player ID before using it to construct an S3 object key.

The object key is generated by Lambda:

```python
object_key = f"players/{player_id}.json"
```

For example, a player's save file follows this structure:

```text
players/
└── COGNITO_PLAYER_ID.json
```

The game client does not choose the player ID or submit an arbitrary S3 object key. This prevents the client from requesting a URL for another player's save file by simply changing an ID in its request.

The player's Cognito `sub` is used because it is a unique identifier for the user within the User Pool.

## 5. Private Amazon S3 Storage

The S3 bucket `godot-cloud-1` stores player save files.

The bucket is configured with the following security settings:

- Block Public Access is enabled.
- Access Control Lists (ACLs) are disabled.
- Server-side encryption with Amazon S3 managed keys (SSE-S3) is enabled by default.
- Bucket versioning is disabled.
- Player save files are stored under the `players/` prefix.

The bucket is not publicly accessible. Players cannot download save files simply by knowing their object keys.

S3 encryption at rest protects stored object data. HTTPS protects data while it is being transferred between the application and AWS services.

## 6. IAM Permissions

The Lambda function uses the IAM role `GodotProject1LambdaRole`.

The role has the following permissions:

- `s3:PutObject` — allows the function to generate upload URLs for player objects.
- `s3:GetObject` — allows the function to generate download URLs for player objects.

The custom IAM policy is named `GodotProject1PlayerDataAccess`.

Its resource restriction is:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::godot-cloud-1/players/*"
    }
  ]
}
```

These permissions are restricted to objects inside the `players/` prefix of the project bucket.

The Lambda role also uses the AWS-managed `AWSLambdaBasicExecutionRole` policy for basic execution and CloudWatch logging permissions.

The function does not need broad S3 permissions such as `s3:*`.

## 7. Presigned URLs

The Lambda function does not receive or store the player's complete save file.

Instead, it generates a temporary presigned URL that allows the Godot application to communicate directly with S3.

There are two supported actions:

### Upload

When the requested action is `upload`, Lambda generates a presigned S3 PUT URL.

The URL is generated with the following settings:

- Bucket: `godot-cloud-1`
- Object key: `players/{player_id}.json`
- Content type: `application/json`
- Expiry: 300 seconds

The Godot application uses the URL to upload the JSON save file directly to S3.

### Download

When the requested action is `download`, Lambda generates a presigned S3 GET URL for the authenticated player's object.

The Godot application uses this URL to download the save file directly from S3.

### Why presigned URLs are useful

Presigned URLs allow the game client to access a private S3 object without receiving AWS access keys or having direct IAM credentials.

They are temporary and restricted to the operation for which they were generated.

A URL is valid for up to five minutes. Anyone who obtains a valid URL may be able to use it for its permitted operation until it expires, so the application should not expose or unnecessarily log these URLs.

## 8. Data Transfer Flow

The upload and download processes use different connections for authorisation and file transfer.

### Upload

1. The player signs in through Cognito.
2. Cognito returns an access token.
3. Godot sends an authenticated POST request to API Gateway, asking for an upload URL.
4. API Gateway validates the JWT.
5. Lambda reads the verified player identity and generates a presigned PUT URL.
6. API Gateway returns the URL to Godot.
7. Godot uploads the JSON save file directly to S3 using HTTPS.

### Download

1. The player signs in through Cognito.
2. Godot requests a download URL using the access token.
3. API Gateway validates the JWT.
4. Lambda obtains the player's identity and generates a presigned GET URL.
5. API Gateway returns the URL to Godot.
6. Godot downloads the JSON save file directly from S3 using HTTPS.

The complete save file does not pass through API Gateway or Lambda. This reduces the amount of data handled by the backend and avoids using Lambda as a file-transfer service.

## 9. Password Reset Security

The password-reset process is handled directly by Cognito.

When a player requests a password reset, Godot sends a `ForgotPassword` request to Cognito. Cognito sends a verification code to the player's registered email address.

The player then enters the code and a new password. Godot sends these details to Cognito using `ConfirmForgotPassword`.

The password and verification code are not sent through API Gateway or Lambda, and they are not stored in S3.

## 10. Current Security Limitations

This is a learning project, so some additional security features have not yet been implemented.

**Token refresh**

The application does not currently refresh expired access tokens automatically. When a token expires, the player may need to sign in again.

**Logout**

The current logout function clears the locally stored tokens from the Godot application. It does not perform a remote Cognito sign-out or revoke the refresh token.

**Multi-factor authentication**

MFA is not currently implemented in the Godot authentication flow.

**Advanced authentication challenges**

Additional Cognito authentication challenges, such as MFA challenges and new-password challenges, are not currently handled.

**Request rate limiting**

The application does not currently implement a dedicated rate-limiting strategy for authentication or URL-generation requests.

**Token storage**

Tokens are held in application memory. Persistent, encrypted token storage has not been implemented.

**Save-file integrity**

The application validates the structure of downloaded JSON data, but it does not currently provide cryptographic signatures or application-level encryption for save files.

These limitations are important when considering the project for production use. Additional controls would be needed before using this implementation for a public game with real players and valuable player data.

## 11. Security Summary

Project 1 uses Cognito for authentication, API Gateway for JWT validation, Lambda for identity-based URL generation, IAM for restricted S3 permissions and private S3 storage for player save files.

The most important security decision is that the game client never decides which player's S3 object it can access. Lambda derives the object key from the authenticated Cognito identity and generates a temporary URL for that specific object.

This creates a simple separation of responsibilities:

- **Cognito:** manages user accounts and authentication.
- **API Gateway:** validates access tokens.
- **Lambda:** verifies the expected claims and generates player-specific presigned URLs.
- **IAM:** restricts the Lambda function's S3 permissions.
- **S3:** stores private player save files and handles direct file transfers.

The result is a relatively simple and cost-conscious cloud-save architecture that demonstrates several important AWS security concepts.
